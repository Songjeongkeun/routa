# 이희승 담당 업무 — 추천 경로 계산·외부 API

## 1. 한눈에 보기

| 항목 | 내용 |
|---|---|
| 담당 기능 | 장소 정보 보완, 대중교통 조회, 시간 검증, 추천 코스 계산, 계산 상태 |
| 관련 요구사항 | `FR-09~27`, `FR-36`, `FR-37`, `FR-46`의 서버 계산 부분 |
| 직접 관련 화면 | `SCR-018 경로 생성 중`의 상태 데이터 |
| 결과를 제공하는 화면 | `SCR-014`, `SCR-016~020` |
| 권장 브랜치 | `feature/route-recommendation` |
| 핵심 완료 조건 | 유효한 입력으로 최대 3개 코스를 만들고, 외부 API 실패·취소까지 예측 가능한 상태로 반환함 |

이 업무는 화면보다 서버 계산 비중이 크다. 조주영의 `tripPlan`을 입력으로 받아 장소와 이동 정보를 검증하고, 송정근의 지도·타임라인 화면이 사용할 일정 데이터를 만든다.

## 2. 담당 범위와 경계

### 직접 구현하는 것

- 관광지·음식점 후보 조회와 내부 형식 변환
- 운영시간·휴무·입장 마감·반려동물 출입 검증
- ODsay 기반 구간별 대중교통 정보 조회
- 도착·방문 시작·방문 종료시간 계산
- 이동 완충시간, 고정 일정, 첫차·막차, 종료 조건 검사
- 식사 노드 배치와 90분 확보 검사
- 방문 순서 탐색과 최대 3개 코스 생성
- 추천 실행 상태 조회·취소·부분 성공 처리
- 일정 재계산에 사용할 서버 함수

### 다른 담당자가 구현하는 것

- `SCR-018`의 로딩 화면 자체: 송정근
- `SCR-014`의 지도·타임라인·코스 카드: 송정근
- 여행 입력 단계와 `tripPlan` 저장: 조주영
- 로그인·소유권 인증 기반: 박현규

## 3. 백엔드 담당 파일

```text
Server/src/modules/recommendations/
├── recommendation.router.mjs
├── recommendation.controller.mjs
├── recommendation.service.mjs
├── recommendation.repository.mjs
└── recommendation.scorer.mjs

Server/src/providers/
├── tourApi.mjs      # TOUR API 장소·반려동물 상세
├── odsay.mjs        # 시간대별 대중교통 경로
├── kakao.mjs        # 장소 검색·좌표
└── google.mjs       # 영업시간·평점 등 장소 보완
```

Google·카카오 OAuth 로그인은 박현규 담당이다. 여기서는 장소·좌표·영업정보 API만 다룬다.

## 4. 담당 API

```text
POST /api/trip-plans/:tripPlanId/recommendations
GET  /api/recommendations/:runId
POST /api/recommendations/:runId/cancel
```

공통 응답과 오류 형식은 [전체 API 구조 설계서](<./전체_구조_ ROUTA_API_STRUCTURE.md>)를 따른다.

### 상태 값

| 상태 | 의미 | 화면 처리 |
|---|---|---|
| `QUEUED` | 계산 대기 | 로딩 유지 |
| `RUNNING` | 계산 진행 중 | 현재 처리 단계 표시 |
| `SUCCEEDED` | 전체 성공 | `SCR-014`로 이동 |
| `PARTIAL` | 일부 외부 데이터 실패, 사용 가능한 결과 있음 | 누락·확인 필요 경고와 결과 표시 |
| `FAILED` | 유효한 결과 생성 실패 | 실패 사유와 조건 수정 행동 표시 |
| `CANCELLED` | 사용자 또는 서버가 취소 | `SCR-013`으로 복귀 |

계산 시작은 `202 Accepted`와 `runId`를 반환하고, 같은 요청의 중복 실행 방지 정책을 둔다.

## 5. 계산 순서

1. `tripPlanId`의 소유권과 필수 입력을 검사한다.
2. Kakao Local API로 후보와 좌표를 조회한다.
3. Google Places로 영업시간·휴무·평점 등 부족한 정보를 보완한다.
4. 반려동물 동반이면 TOUR API로 출입 가능 여부와 세부 조건을 교차 검증한다.
5. 장소를 출발·방문·식사·종료 노드로 변환한다.
6. ODsay로 노드 사이의 시간대별 대중교통 구간을 조회한다.
7. 방문시간·운영시간·고정 일정·식사·막차·종료 조건을 검사한다.
8. Branch-and-Bound로 유효한 방문 순서를 탐색한다.
9. 최단 도보, 최소 이동시간, 종합 추천 코스를 최대 3개 만든다.
10. itinerary·items·legs·검증 경고를 저장하고 결과 ID를 반환한다.

## 6. 반드시 지킬 계산 규칙

### 시간 계산

```text
예상 도착시간 = 이전 장소 출발시간 + 구간 이동시간 + 이동 완충시간
방문 시작시간 = max(예상 도착시간, 장소 운영 시작시간)
방문 종료시간 = 방문 시작시간 + 체류시간
```

- 일반 이동 완충시간: 기본 10분
- 반려동물 동반 이동 완충시간: 15분
- 고정 일정 전 완충시간: 최소 20분
- 장소 체류시간: 입력된 30분 단위 값 사용
- 점심·저녁 식사시간: 모두 **90분**
- 점심 권장 시작: `11:00~14:00`
- 저녁 권장 시작: `17:00~20:00`
- 음식점 검색: 500m부터 시작해 후보가 없으면 1km까지 확대
- 대체 관광지: 1km부터 시작해 없으면 500m씩 확대하고 자동 추가하지 않음

### 코스 종류

| 값 | 선정 기준 |
|---|---|
| `SHORTEST_WALK` | 총 도보거리가 가장 짧음 |
| `FASTEST_TRANSIT` | 총 이동시간이 가장 짧음 |
| `BALANCED` | 시간 가중치 `0.7`, 거리 가중치 `0.3`을 기본으로 종합 평가 |

세 코스가 항상 서로 달라야 하는 것은 아니다. 조건을 만족하는 코스가 1~2개뿐이면 실제 생성 수와 이유를 명확히 반환한다.

### 반려동물 정보

- `불가` 후보는 제외한다.
- `가능`은 근거 정보와 세부 조건을 저장한다.
- `확인 불가`를 임의로 가능·불가로 바꾸지 않고 경고와 연락처 또는 확인 방법을 반환한다.
- 이동 구간에는 케이지, 대형견 제한 가능성, 운영기관 확인 필요성을 표시할 수 있는 데이터를 포함한다.

## 7. 외부 API 구현 규칙

- API 키는 서버 환경변수에서만 읽고 프론트나 로그에 노출하지 않는다.
- `searchKeyword2` 같은 키워드 파라미터는 URL 인코딩된 값을 전송한다.
- provider가 외부 응답을 ROUTA 내부 DTO로 변환하며 원본 응답을 controller에서 직접 반환하지 않는다.
- 각 호출에 timeout·제한된 재시도·rate limit 대응을 둔다.
- 동일 장소·동일 구간 조회는 가능한 범위에서 캐시한다.
- 출처, 조회 시각, 원본 식별자를 저장해 충돌과 오래된 정보를 추적할 수 있게 한다.
- 외부 API 하나가 실패해도 가능한 결과가 있으면 `PARTIAL`로 처리한다.

## 8. 다른 담당자와 맞춰야 할 내용

| 담당자 | 받을 것 | 내가 제공할 것 |
|---|---|---|
| 박현규 | 인증 사용자·소유권 검사 방식 | 추천 실행 리소스의 소유권 검사 적용 |
| 조주영 | `tripPlanId`, 날짜·시간·장소·체류시간·테마·식사·반려동물 조건 | 보완된 장소 DTO와 입력 검증 오류 |
| 송정근 | 화면이 요구하는 Mock 필드와 재계산 요청 | `runId`, 상태, 최대 3개 `itineraryId`, summary/items/legs/warnings, 재계산 함수 |

송정근에게 전달할 결과는 최소한 다음 구조를 가져야 한다.

```text
itineraryId, courseKind
summary(totalMinutes, walkingDistanceMeters, transferCount, estimatedFare)
items(order, kind, place, arrivalTime, startTime, endTime, stayMinutes)
legs(fromItemId, toItemId, transit, duration, walkDistance, transfers, fare)
warnings(code, message, placeId 또는 legId, confirmationRequired)
```

## 9. 구현 순서

1. 송정근과 결과 DTO·Mock 데이터를 먼저 확정한다.
2. 각 provider를 단독 호출하고 내부 DTO 변환 테스트를 작성한다.
3. recommendation run 생성·상태·취소 API를 구현한다.
4. 노드·구간·방문시간 계산을 구현한다.
5. 운영시간·반려동물·고정 일정·식사·막차·종료 조건을 구현한다.
6. 방문 순서 탐색과 세 코스 점수 계산을 구현한다.
7. itinerary와 구간 정보를 저장한다.
8. `PARTIAL`, `FAILED`, `CANCELLED` 및 timeout을 테스트한다.
9. 송정근의 로딩·결과·편집 화면과 실제 응답을 연결한다.

## 10. 완료 체크리스트

- [ ] 유효한 `tripPlanId`로 계산을 시작하고 `202`와 `runId`를 반환한다.
- [ ] 로딩 화면이 상태와 현재 처리 단계를 조회할 수 있다.
- [ ] 취소 요청 후 상태가 `CANCELLED`가 되고 입력 화면으로 복귀할 수 있다.
- [ ] 필수 방문지, 운영시간, 고정 일정, 식사, 막차, 종료 조건을 모두 검사한다.
- [ ] 일반 10분·반려동물 15분·고정 일정 전 20분 완충시간을 적용한다.
- [ ] 모든 식사 노드에 90분을 적용한다.
- [ ] 최대 3개 코스에 동일한 비교 지표와 방문 순서를 제공한다.
- [ ] 반려동물 불가 후보는 제외하고 확인 불가는 경고로 남긴다.
- [ ] 외부 API timeout이 서버 요청을 무기한 대기시키지 않는다.
- [ ] 부분 실패에서도 가능한 결과가 있으면 `PARTIAL`과 경고를 반환한다.
- [ ] 송정근이 `itineraryId`로 전체 지도·타임라인 데이터를 조회할 수 있다.
